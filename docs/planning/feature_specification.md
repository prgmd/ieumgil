## 01. 문서 개요 · 용어 · 우선순위 기준

본 문서는 이음길 서비스의 화면별 기능 요구사항을 정의한다. 각 요구사항은 고유 ID를 가지며, 이슈 트래커(Jira)의 Epic/Story와 1:1로 매핑하는 것을 권장한다.

### 용어

| 용어 | 정의 |
|---|---|
| **그룹** | 함께 여행하는 사람들의 모임 단위. 여러 프로젝트를 가질 수 있다. |
| **프로젝트** | 한 번의 여행 단위. 상태는 `계획 중(PLANNING)` ↔ `완료(DONE)`로 **양방향 전환**된다(완료는 잠금이 아니라 표시용 상태 값). |
| **블록** | 일정 편집의 최소 단위. 카테고리·시간·예산·세부 내용을 가진다. |
| **체인** | 블록이 시각 순으로 이어진 일정 라인. 편집 화면에서는 여행 전체가 하나의 세로 스크롤 축이며, Day는 저장값이 아니라 각 블록의 절대 오프셋에서 파생되는 구간이다. Day 탭은 그 축 위의 위치 표시 + 점프 컨트롤이다(화면을 갈아끼우지 않는다). |
| **후보 블록** | 체인에 넣지 않고 보관 중인 블록(단일 리스트). 챗봇·지도에서 만든 블록과 체인에서 뺀 블록이 모인다. |
| **열람 모드** | 보드를 읽기 전용으로 보는 **보기 옵션**. 사용자가 직접 켜고 끄며, 프로젝트 상태와 무관하게 언제든 해제할 수 있다. |
| **op** | 블록 생성/수정/이동/삭제 등 하나의 변경 이벤트. 서버가 순서를 부여해 전원에게 브로드캐스트. |

### 우선순위 기준

| 우선순위 | 의미 |
|---|---|
| **필수** | MVP에 반드시 포함 (없으면 시연 불가) |
| **권장** | 1차 릴리즈 목표 (차별화 요소) |
| **선택** | 시간 여유 시 (제외해도 서비스 성립) |

## 02. 사용자 역할 및 권한

| 역할 | 정의 | 권한 |
|---|---|---|
| **비로그인** | 로그인 전 사용자 | 메인페이지 열람, 소셜 로그인만 가능 |
| **회원** | 소셜 로그인 완료 | 그룹 생성, 초대 코드로 그룹 입장 |
| **멤버** | 그룹에 속한 회원 | 그룹 내 프로젝트 CRUD, 블록 편집, 보이스 참여 |
| **관리자(방장)** | 그룹을 생성한 회원 | 멤버 권한 전체 + 멤버 방출, 초대 코드 재발급, 그룹 삭제 |

> **참고** — 방장이 그룹을 탈퇴하는 경우: 가입일이 가장 오래된 멤버에게 관리자 권한 자동 위임. 마지막 1인이 탈퇴하면 그룹은 소프트 삭제된다.

> **[2026-08-05 갱신]** 범위 제외 — 방장/권한(role) 모델 미도입(flat 모델, role 컬럼 없음). 위 "관리자(방장)" 역할 행과 방장 자동 위임 문단 무효, 전 멤버 동등. 그룹명 수정·초대코드 재발급·멤버 방출 등 "관리자 전용" 권한은 폐기(방출·수동 그룹 삭제는 기능 자체 제거 — MY-04 2026-08-08 갱신 참조, 그룹 소멸은 GRP-09 전원 탈퇴로 일원화. 그룹명 수정·초대코드 재발급은 전 멤버가 수행). 마지막 1인 탈퇴는 소프트 삭제가 아니라 하드 삭제로 변경(GRP-09 참조).

## 03. 화면 흐름

```
메인페이지 (로그인)
 └─ 개인 페이지 ─ 내 그룹 목록 · 초대 코드 입장
     └─ 그룹 페이지 ─ 프로젝트 목록 · 멤버 관리
         ├─ [계획 중/여행 중] 카드 클릭 → 프로젝트 대시보드 (Day 탭 · 챗봇 FAB · 보이스)
         └─ [지난 여행] 카드 클릭 → 프로젝트 대시보드 (편집 가능 · 열람 모드 토글 제공)
                └─ ※ 완료 표시는 프론트가 여행 종료시각(endDate) 경과로 파생 — 수동 전환 버튼 없음(GRP-10 갱신 참조)
```

## 04. A. 메인페이지 `AUTH`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `AUTH-01` | **랜딩 화면** | 이음길 로고, 서비스 한 줄 소개, 로그인 버튼 2종. | 필수 |
| `AUTH-02` | **카카오 로그인** | 카카오 OAuth 2.0 인가 코드 방식. 수집 항목: 닉네임, 프로필 이미지(선택). 최초 로그인 시 자동 회원가입 처리. | 필수 |
| `AUTH-03` | **네이버 로그인** | 네이버 OAuth 2.0. 동일 이메일이라도 카카오/네이버는 별도 계정으로 취급 (계정 통합 미지원 — v1 범위 외). | 권장 |
| `AUTH-04` | **토큰 관리** | 자체 JWT 발급 — Access 30분 / Refresh 14일. Refresh는 HttpOnly Secure 쿠키, Access는 메모리 보관. 재발급 API 제공. | 필수 |
| `AUTH-05` | **로그아웃 / 탈퇴** | 로그아웃: Refresh 무효화(Redis 블랙리스트). 탈퇴: 개인정보 즉시 삭제, 작성한 블록은 그룹 자산으로 유지하되 작성자를 "탈퇴한 멤버"로 표기. | 권장 |

> **[2026-08-05 갱신] AUTH-01** — 변경: 로그인 버튼 1종(카카오)만. 네이버 버튼 없음.
> **[2026-08-05 갱신] AUTH-03** — 범위 제외 확정(2026-08-05): 네이버 로그인 미구현(코드 전무).
> **[2026-08-05 갱신] AUTH-05** — 변경: 로그아웃은 Redis 블랙리스트가 아니라 서버 저장 Refresh(RTR) 삭제 방식(RTR이라 등가). 탈퇴는 `DELETE /api/members/me` + 작성자 "탈퇴한 멤버" 표기로 구현.
> **[2026-08-07 갱신] AUTH-05** — 추가 구현: 로그아웃·탈퇴 시 열려 있는 WS 세션도 강제 종료. 탈퇴 계정의 유효 토큰은 이후 모든 보호 API에서 `COMMON401`(`ActiveUserChecker`). / 알려진 한계: 회원 탈퇴의 소속 그룹 일괄 탈퇴는 `MEMBER_LEFT` op를 발행하지 않아, 열려 있던 대시보드의 멤버 목록이 새로고침 전까지 갱신되지 않는다.

## 05. B. 개인 페이지 `MY`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `MY-01` | **그룹 목록 조회** | 내가 속한 그룹을 카드 그리드로 표시. 카드 정보: 그룹명, 멤버 수, 완료된 프로젝트 수. 클릭 시 그룹 페이지 진입. | 필수 |
| `MY-02` | **그룹 생성** | 입력: 그룹명(2~20자, 필수). 생성자는 자동으로 관리자. 생성 직후 초대 코드가 발급되어 공유 모달 표시. | 필수 |
| `MY-03` | **그룹 수정** | 그룹명 인라인 편집. 관리자만 가능. | 권장 |
| `MY-04` | **그룹 삭제** | 관리자만. 확인 모달에서 그룹명을 직접 입력해야 삭제(오삭제 방지). 소프트 삭제 30일 후 완전 삭제. | 권장 |
| `MY-05` | **초대 코드 입장** | 코드 입력 필드(8자리, 영대문자+숫자 — 혼동되기 쉬운 `I·O·0·1`은 제외, 예: `YJ3K7Q2M`). 유효한 코드면 즉시 그룹 가입 + 그룹 페이지 이동. 실패 사유 구분: 형식 오류 / 존재하지 않음 / 만료됨 / 정원 초과(최대 10명). | 필수 |

> **[2026-08-05 갱신] MY-01** — 변경: 카드의 프로젝트 수는 "완료된" 수가 아니라 전체 프로젝트 수(tripCount).
> **[2026-08-05 갱신] MY-02** — 변경: 관리자 개념 없음(flat) — "생성자는 자동 관리자" 무효. 생성 + 초대코드 공유 모달은 구현.
> **[2026-08-05 갱신] MY-03** — 변경: 그룹명 수정은 관리자 한정 아님 — 전 멤버 가능.
> **[2026-08-05 갱신] MY-04** — 변경: 그룹 삭제 관리자 한정 폐기(전 멤버 가능), 이름 입력 확인 모달은 구현. / 30일 후 완전 삭제(퍼지)는 **구현됨** — `GroupCleanupScheduler`(매일 04:00 cron)가 소프트 삭제 30일 경과분을 `deleteAllSoftDeletedBefore`로 하드 삭제.
>
> **[2026-08-08 갱신] MY-04 — 기능 제거.** 수동 그룹 삭제를 폐기한다. flat 모델에서 한 멤버가 공용 그룹을 삭제하면 전원의 데이터가 사라지는 위험이 있고(나가기로 오인해 삭제한 사고도 있었다), 삭제 버튼·모달·REST 엔드포인트(`DELETE /groups/{id}`)·`softDeleteGroup` 서비스·전용 DTO·`GroupCleanupScheduler`를 모두 제거했다. 그룹 소멸은 GRP-09(전원 퇴장 시 하드 삭제)로 일원화한다. `deletedAt` 필터 인프라는 유지.

## 06. C. 그룹 페이지 `GRP`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `GRP-01` | **프로젝트 목록** | 카드 리스트. 정보: 프로젝트명, 여행 기간, 목적지·여행 인원·주요 교통수단(GRP-02에 입력한 값이 있을 때만 표시), 상태 배지(계획 중/완료), 썸네일(프로젝트 생성 시 자동 배정되는 테마 컬러 그라데이션 — 사용자 업로드 아님). 상태별 카드 클릭 동작은 GRP-05 참조. | 필수 |
| `GRP-02` | **프로젝트 생성** | 입력: 프로젝트명(필수), 목적지(자유 텍스트, 선택), 여행 인원(1 이상, 기본 4 — 정산 기준 인원의 초기값으로 사용, BGT-03), 여행 시작일·종료일(캘린더 선택, 필수 — Day 수 자동 산출), 주요 교통수단(선택형: KTX/기차·버스·자가용·비행기·대중교통 — 프로젝트 정보로 저장되어 그룹 페이지 카드에 표시, GRP-01). **희망 총 예산은 이 모달에서 받지 않는다** — 생성 후 대시보드 예산 위젯에서 설정한다(BGT-02). 목적지·여행 인원·교통수단은 챗봇 이음이의 추천 컨텍스트로도 함께 활용된다(BOT-03).<br>**챗봇 미사용 케이스**: 챗봇은 끝까지 쓰지 않아도 되며, 이는 오류가 아닌 정상 상태다. 미사용 시 챗봇 추천만 일어나지 않고 지도 검색(MAP-02·MAP-03)·직접 추가로 모든 기능을 정상 이용할 수 있다(무기한 재촉 금지 — BOT-01·POOL-01의 빈 상태 문구로만 유도한다). | 필수 |
| `GRP-03` | **프로젝트 수정** | 이름·기간 수정. 기간이 줄어 사라지는 Day의 블록은 삭제하지 않고 후보 블록으로 자동 이동. | 권장 |
| `GRP-04` | **프로젝트 삭제** | 멤버 누구나 요청 가능하나 확인 모달 필수. 완료된 프로젝트 삭제는 관리자만. | 권장 |
| `GRP-05` | **프로젝트 카드 진입 분기** | **카드 클릭**: 상태와 무관하게 **프로젝트 대시보드로 진입하며 편집이 가능하다**(완료 프로젝트도 동일 — RO-01). 완료 프로젝트는 진입 시 상단에 안내 배너 + 열람 모드 토글이 함께 표시된다. | 필수 |
| `GRP-06` | **멤버 목록 · 초대** | 멤버 리스트(프로필, 닉네임, 방장 뱃지, 접속 상태). 초대 코드 표시 + 복사 버튼. 관리자는 코드 재발급 가능(기존 코드 즉시 무효화). 코드 유효기간 7일. | 필수 |
| `GRP-07` | **멤버 방출** | 관리자만. 확인 모달 후 즉시 그룹 접근 차단. 방출된 멤버의 블록은 유지(작성자 표기 유지). 방출자는 동일 코드로 재입장 불가(코드 재발급 필요). | 권장 |

## 07. D. 프로젝트 대시보드 `DASH`

서비스의 핵심 화면. **3단 레이아웃** — 좌측 Day 탭 컬럼 / 중앙 보드(체인 + 후보 블록) / 우측 위젯(예산·지도·장소 검색). 접속 중인 멤버는 상단 바 아바타로 표시한다(PRS-01). 챗봇은 우하단 플로팅 버튼, 보이스는 하단 중앙 고정 바. 편집 모드의 체인 영역은 자체 스크롤 컨테이너(최대 높이 제한)로 동작하며, 그 안에 **여행 전체가 이어진 하나의 세로 축**이 들어간다(DAY-01) — 블록이 아무리 늘어도 페이지 전체를 크게 스크롤하지 않고 하단의 후보 목록이 항상 함께 보인다. 모든 편집은 실시간으로 전 멤버에게 동기화된다(NFR-01).

### D-1. Day 탭 `DAY`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `DAY-01` | **Day 탭 네비게이션** | 보드 **좌측에 세로로 고정된 책갈피 형태의 탭 컬럼**으로 DAY 1 ~ DAY n을 자동 생성해 나열한다(가로 스크롤 탭 바 아님). 각 탭에 해당 Day의 블록 개수 뱃지 표시. **탭은 화면을 갈아끼우는 필터가 아니라 위치 표시 + 점프 컨트롤이다** — 편집 타임라인은 여행 전체가 이어진 하나의 세로 스크롤 축이고, 탭을 누르면 그 Day의 첫 블록으로 스크롤한다(빈 Day는 그 Day의 00:00). 활성 탭(진한 배경 + 액센트 컬러 테두리)은 클릭이 아니라 **스크롤 위치에서 파생**된다 — 화면을 가장 많이 차지하는 Day가 활성이다. 일자 헤더는 축 위에 Day 경계마다 놓인 반투명 sticky 구분선으로, 카드가 그 밑을 지나간다(자정을 넘는 블록이 한 카드로 이어진다). 헤더에는 날짜를 표시하며, **시작 시각·종료 예상 시각 표시는 아직 미구현이다**(이 항목은 연속 축 전환 이전부터 미구현이었고 범위에서 빠진 것이 아니다). 탭 컬럼은 보드 스크롤과 무관하게 상단에 sticky로 고정된다. 최대 14일(NFR-04) 기준으로 검증하며, 그 이상은 탭 컬럼 자체가 세로 스크롤된다. 열람 모드에서는 숨겨진다(RO-02). | 필수 |
| `DAY-02` | **Day 간 블록 이동** | 블록을 다른 Day로 옮긴다. 편집 축이 여행 전체 한 줄이므로 **탭 드롭이라는 별도 조작 없이 카드를 위아래로 끌어 목적지 Day의 시각에 놓는 것**이 곧 일자 이동이다(먼 Day는 드래그 중 스크롤·자동 스크롤로 도달). 놓인 자리의 절대 오프셋이 그대로 저장되고(`startOffsetMinutes`), Day 소속은 저장값이 아니라 오프셋에서 파생되므로(`offset / 1440 + 1`) 카드 위치·탭 개수 뱃지·지도·열람 모드가 함께 따라온다. 삽입 위치 프리뷰는 축 위의 고스트로 표시된다(BLK-07). | 필수 |

| `BGT-04` | **인원 변동 이력 안내** | 프로젝트 진행 중 정산 기준 인원이 바뀌면 활동 로그에 기록한다("○○님 합류 — 정산 인원 4→5명"). **희망 총 예산 게이지(BGT-02)는 팀 총액 기준이므로 인원 변동의 영향을 받지 않는다** — 게이지는 그대로 두고, 1인 값(BGT-03)만 함께 갱신된다. | 선택 |

## 08. E. 열람 모드 `RO`

보드를 읽기 전용으로 보는 **보기 옵션**이다. 완료된 프로젝트를 "계획했던 블록을 다시 본다"는 목적으로 훑을 때, 또는 편집 중 실수로 블록을 건드리고 싶지 않을 때 사용한다.

> **전제 — 완료는 잠금이 아니다.** 프로젝트 상태(`PLANNING` ↔ `DONE`)는 표시용 값일 뿐이며, **완료 후에도 모든 편집이 가능하다**(GRP-10). 여행 중 바뀐 일정을 사후에 기록하거나, 실수로 누른 완료를 되돌리거나, 빠뜨린 세부 내용을 나중에 채워 넣는 일은 모두 정상 시나리오다. 열람 모드는 사용자가 **직접 켜고 끄는 토글**이며, 프로젝트 상태와 무관하게 시스템이 강제로 적용하지 않는다.

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `RO-01` | **열람 모드 토글** | 대시보드 상단에 편집/열람 모드 토글을 상시 제공한다. 프로젝트 상태(계획 중/완료)와 무관하게 언제든 켜고 끌 수 있으며, **켜짐 상태는 본인 화면에만 적용된다**(클라이언트 로컬 설정 — 다른 멤버의 편집을 막지 않는다. 서버 전송·DB 저장 없음). 프로젝트 상태에 따른 기본값 차등(예: 완료 시 자동 켜짐)은 두지 않는다 — 진입 시 항상 마지막으로 선택한 모드를 유지한다. | 필수 |

## 09. 비기능 요구사항 `NFR`

| ID | 항목 | 사양 |
|---|---|---|
| `NFR-01` | **실시간 동기화** | WebSocket + STOMP. 프로젝트 단위 토픽 `/topic/project/{id}`. 모든 변경은 서버 검증 → DB 반영 → 순서 번호(seq)를 붙인 op로 브로드캐스트(서버 권위 모델). 클라이언트는 낙관적 UI 적용 후 서버 op로 확정/롤백. 재연결 시 마지막 수신 seq 이후 op 재전송 또는 스냅샷 재로딩. |
| `NFR-02` | **동시성 — 필드/순서** | **블록 필드: 필드 단위 LWW(Last-Write-Wins)**.<br>· op는 **변경된 필드만** 담아 전송한다(`{block_id, field, value, client_ts}`). 서버는 `UPDATE block SET <field>=?, <field>_updated_at=? WHERE id=? AND <field>_updated_at < ?` 형태로 **해당 필드만** 갱신하고, 더 오래된 op는 조용히 무시한다<br>· 서로 다른 필드에 대한 동시 편집은 **구조적으로 충돌하지 않는다**(예산과 소요 시간은 독립). 같은 필드 동시 편집만 나중 값이 이기며, 진 쪽에는 서버 op로 최신값이 밀려와 화면이 정정된다<br>· 시각 기준은 **서버 수신 시각**을 사용한다(클라이언트 시계 신뢰 금지). 필드별 갱신 시각의 스키마 형태는 OI-04<br>· **긴 텍스트 필드는 예외** — NFR-03 참조<br>**블록 순서**: fractional indexing 문자열 키 — 이동 시 1행만 갱신, 동시 삽입도 충돌 없음. Day 간 이동도 같은 경로다 — Day와 시각이 `start_offset_minutes` 한 값이라 `start_offset_minutes` + `order_key` 동시 갱신 1건이면 끝난다. |
| `NFR-03` | **동시성 — 긴 텍스트 필드** | 세부 내용(최대 500자)은 LWW를 그대로 적용하면 **입력 중이던 문장 전체가 통째로 날아가는** 유일한 필드다. 정책 후보는 아래 두 가지이며 **구현 담당자 간 합의로 결정한다(OI-04)**:<br>· **(a) 텍스트 필드 한정 편집 락** — Redis `SET NX`, TTL 30초 + 10초 하트비트. 락 보유자만 저장 가능, 타 멤버는 해당 **텍스트 영역만** 읽기 전용(블록의 다른 필드는 자유롭게 편집 가능). 구현 단순, 동시 작성 불가<br>· **(b) 필드 단위 LWW + 덮어쓰기 경고** — 저장 시점에 서버 값이 내가 연 시점보다 새로우면 저장을 보류하고 diff 안내("○○님이 먼저 수정했어요 — 덮어쓰기 / 내 변경 취소"). 락 없음, 구현 중간, 동시 작성 시 한쪽 손실<br>권고: v1은 (a). 텍스트 필드는 편집 빈도가 낮아 락 대기의 체감 비용이 작고, 락 범위가 블록이 아닌 필드로 좁으므로 협업을 막지 않는다.<br>**1회성 작업**(챗봇 초기 생성 등)은 위 논의와 무관하게 Redis 분산 락으로 중복 실행 방지. |
| `NFR-04` | **성능 목표** | op 브로드캐스트 왕복 < 300ms(동일 리전), 대시보드 최초 로딩 < 2s, 프로젝트당 블록 최대 200개·Day 최대 14일, 동시 접속 그룹당 10명 기준 무리 없는 동작. |
| `NFR-05` | **보안** | 모든 API JWT 인증. 그룹 리소스 접근 시 멤버십 검증(서버). **프로젝트 상태(`DONE`)에 따른 쓰기 op 거부는 두지 않는다** — 완료는 표시용 상태 값이며 편집 권한은 상태와 무관하게 그룹 멤버십으로만 판정한다(RO-01). 초대 코드는 추측 불가 랜덤 8자(혼동되는 `I·O·0·1` 제외) + 7일 만료 + 재발급 시 무효화. WebSocket 연결 시에도 토큰 검증. |

> **[2026-08-05 갱신] NFR-03 / OI-04** — 결정 완료: **(a) Redis 편집 락** 채택·구현(`DetailLockService`, `SET NX` · TTL 30s · 하트비트 · 소유자 한정 해제). `field_updated_at`은 **JSON 단일 컬럼**으로 확정.

## 11. 데이터 모델 개요

```
member (id, provider, provider_id, nickname, profile_img, created_at)
group_ (id, name, invite_code, invite_expires_at, owner_id, deleted_at)
group_member (group_id, member_id, role[ADMIN|MEMBER], joined_at)
project (id, group_id, name, start_date, end_date,
         destination(GRP-02·nullable), main_transport(GRP-02·nullable),
         keywords(챗봇 입력 후 저장·nullable),
         budget_headcount(정산 기준 인원·GRP-02 입력값이 초기값, 이후 직접 재지정 가능),
         budget_target(희망 총 예산·BGT-02·nullable=미설정),
         status[PLANNING|DONE], done_at(되돌리면 null), created_at)
block (id, project_id, start_offset_minutes(Day 1 00:00 기준 경과 분, null=후보),
       order_key(fractional), category, sub_category,
       name, address, duration_min, is_time_fixed(앵커 여부),
       budget(해당 블록의 팀 전체 금액 ─ BLK-01·BGT-01), detail,
       lat, lng, place_id,               ─ 장소성 블록은 lat/lng NOT NULL (MAP-04)
       vehicle_flag[START|END|null],     ─ 차량 구간 표식, ETC 전용 (부록)
       transport_meta(JSON: 수단/열차유형/출발도착 시각·지점 등),
       source[KAKAO|MANUAL|BOT], author_id, last_edited_by(PRS-04),
       field_updated_at(JSON: 필드별 서버 수신 시각 ─ LWW 판정용, NFR-02),
       deleted_at)
activity_log (id, project_id, member_id, op_type, payload, seq, created_at)
```

**설계 원칙**
- `status`는 **양방향 전환**된다(`PLANNING` ↔ `DONE`). 완료를 편집 잠금 조건으로 사용하지 않는다(GRP-10)
- `place_id`에 **UNIQUE 제약을 두지 않는다** — 동일 장소 중복 등록 허용(MAP-03). 장소 식별·재조회용 참조 값으로만 사용
- 블록 단위 `version` 컬럼을 두지 않는다 — 동시성은 `field_updated_at` 기반 필드별 LWW로 처리(NFR-02). 컬럼 분리(`budget_updated_at`, `detail_updated_at` …) vs JSON 단일 컬럼은 **OI-04**에서 결정
- presence(접속·커서)와 텍스트 편집 락은 DB에 저장하지 않고 Redis/메모리에서만 관리한다
- 블록의 위치는 `start_offset_minutes` **하나만** 저장한다(BLK-08). Day 번호·하루 안의 시각·종료 시각·Day 종료 예상 시각은 전부 여기서 파생하며 별도 컬럼을 두지 않는다 — 저장하면 서로 어긋날 수 있기 때문이다
- `block.budget`은 항상 **팀 전체 금액**이다. 1인 금액은 `budget_headcount`로 나눈 파생값이므로 별도 컬럼으로 저장하지 않는다(BGT-01·BGT-03)

> **[2026-08-05 갱신] 데이터 모델 현행화**
> · `group_` / `group_member`: `owner_id`·`role` 컬럼 없음(flat 모델).
> · `project.main_transport`(단수) → `transport_prefs`(jsonb 배열, CAR/PUBLIC 다중). `theme_color` 컬럼은 제거 완료(GRP-01).
> · `field_updated_at`은 JSON 단일 컬럼으로 확정(OI-04).
>
> **[2026-08-07 갱신]** `block.last_edited_by` 구현 완료(마이그레이션 005 — PRS-04). 08-05 노트의 "컬럼 없음" 문구 무효.
>
> **[2026-08-06 갱신]** `block`의 시간 모델 확정: `day_no`·`start_time`·`end_time`·`is_instant`를 두지 않고 `start_offset_minutes`(Day 1 00:00 기준 경과 분, null=후보, CHECK ≥ 0) 하나로 위치를 표현한다. 마이그레이션은 `docker/postgres/migration/006`(이관·인덱스·CHECK)·`007`(옛 컬럼 DROP).
