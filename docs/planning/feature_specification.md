## 01. 문서 개요 · 용어 · 우선순위 기준

본 문서는 이음길 서비스의 화면별 기능 요구사항을 정의한다. 각 요구사항은 고유 ID를 가지며, 이슈 트래커(Jira)의 Epic/Story와 1:1로 매핑하는 것을 권장한다.

### 용어

| 용어 | 정의 |
|---|---|
| **그룹** | 함께 여행하는 사람들의 모임 단위. 여러 프로젝트를 가질 수 있다. |
| **프로젝트** | 한 번의 여행 단위. 상태는 `계획 중(PLANNING)` ↔ `완료(DONE)`로 **양방향 전환**된다(완료는 잠금이 아니라 표시용 상태 값). |
| **블록** | 일정 편집의 최소 단위. 카테고리·시간·예산·세부 내용을 가진다. |
| **체인** | Day별로 블록이 순서대로 연결된 일정 라인. Day 탭으로 전환한다. |
| **후보 블록** | 체인에 넣지 않고 보관 중인 블록(단일 리스트). 챗봇·지도에서 만든 블록과 체인에서 뺀 블록이 모인다. |
| **열람 모드** | 보드를 읽기 전용으로 보는 **보기 옵션**. 사용자가 직접 켜고 끄며, 프로젝트 상태와 무관하게 언제든 해제할 수 있다. |
| **op** | 블록 생성/수정/이동/삭제 등 하나의 변경 이벤트. 서버가 순서를 부여해 전원에게 브로드캐스트. |

### 우선순위 기준

| 우선순위 | 의미 |
|---|---|
| **필수** | MVP에 반드시 포함 (없으면 시연 불가) |
| **권장** | 1차 릴리즈 목표 (차별화 요소) |
| **선택** | 시간 여유 시 (제외해도 서비스 성립) |

## 02. 사용자 역할 및 권한

| 역할 | 정의 | 권한 |
|---|---|---|
| **비로그인** | 로그인 전 사용자 | 메인페이지 열람, 소셜 로그인만 가능 |
| **회원** | 소셜 로그인 완료 | 그룹 생성, 초대 코드로 그룹 입장 |
| **멤버** | 그룹에 속한 회원 | 그룹 내 프로젝트 CRUD, 블록 편집, 보이스 참여 |
| **관리자(방장)** | 그룹을 생성한 회원 | 멤버 권한 전체 + 멤버 방출, 초대 코드 재발급, 그룹 삭제 |

> **참고** — 방장이 그룹을 탈퇴하는 경우: 가입일이 가장 오래된 멤버에게 관리자 권한 자동 위임. 마지막 1인이 탈퇴하면 그룹은 소프트 삭제된다.

## 03. 화면 흐름

```
메인페이지 (로그인)
 └─ 개인 페이지 ─ 내 그룹 목록 · 초대 코드 입장
     └─ 그룹 페이지 ─ 프로젝트 목록 · 멤버 관리
         ├─ [계획 중] 카드 클릭 → 프로젝트 대시보드 (Day 탭 · 챗봇 FAB · 보이스)
         │      └─ "여행 완료" → 상태 전환
         └─ [완료] 카드 클릭 → 프로젝트 대시보드 (편집 가능 · 열람 모드 토글 제공)
                └─ "다시 계획으로" → 상태 되돌리기 (언제든 가능)
```

## 04. A. 메인페이지 `AUTH`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `AUTH-01` | **랜딩 화면** | 이음길 로고, 서비스 한 줄 소개, 로그인 버튼 2종. 밤하늘 비주얼 적용. | 필수 |
| `AUTH-02` | **카카오 로그인** | 카카오 OAuth 2.0 인가 코드 방식. 수집 항목: 닉네임, 프로필 이미지(선택). 최초 로그인 시 자동 회원가입 처리. | 필수 |
| `AUTH-03` | **네이버 로그인** | 네이버 OAuth 2.0. 동일 이메일이라도 카카오/네이버는 별도 계정으로 취급 (계정 통합 미지원 — v1 범위 외). | 권장 |
| `AUTH-04` | **토큰 관리** | 자체 JWT 발급 — Access 30분 / Refresh 14일. Refresh는 HttpOnly Secure 쿠키, Access는 메모리 보관. 재발급 API 제공. | 필수 |
| `AUTH-05` | **로그아웃 / 탈퇴** | 로그아웃: Refresh 무효화(Redis 블랙리스트). 탈퇴: 개인정보 즉시 삭제, 작성한 블록은 그룹 자산으로 유지하되 작성자를 "탈퇴한 멤버"로 표기. | 권장 |

## 06. C. 그룹 페이지 `GRP`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `GRP-01` | **프로젝트 목록** | 카드 리스트. 정보: 프로젝트명, 여행 기간, 목적지·여행 인원·주요 교통수단(GRP-02에 입력한 값이 있을 때만 표시), 상태 배지(계획 중/완료), 썸네일(프로젝트 생성 시 자동 배정되는 테마 컬러 그라데이션 — 사용자 업로드 아님). 상태별 카드 클릭 동작은 GRP-05 참조. | 필수 |
| `GRP-02` | **프로젝트 생성** | 입력: 프로젝트명(필수), 목적지(자유 텍스트, 선택), 여행 인원(1 이상, 기본 4 — 정산 기준 인원의 초기값으로 사용, BGT-03), 여행 시작일·종료일(캘린더 선택, 필수 — Day 수 자동 산출), 주요 교통수단(선택형: KTX/기차·버스·자가용·비행기·대중교통 — 프로젝트 정보로 저장되어 그룹 페이지 카드에 표시, GRP-01). **희망 총 예산은 이 모달에서 받지 않는다** — 생성 후 대시보드 예산 위젯에서 설정한다(BGT-02). 목적지·여행 인원·교통수단은 챗봇 이음이의 추천 컨텍스트로도 함께 활용된다.<br>**키워드 미입력 케이스**: 키워드는 끝까지 입력하지 않아도 되며, 이는 오류가 아닌 정상 상태다. 미입력 시 후보 블록 자동 생성만 일어나지 않고 지도 검색(MAP-02·MAP-03)·직접 추가로 모든 기능을 정상 이용할 수 있다. 알림 뱃지는 사용자가 챗봇 패널을 한 번 연 시점 또는 후보 블록이 1개 이상 생긴 시점에 해제한다(무기한 재촉 금지). | 필수 |
| `GRP-03` | **프로젝트 수정** | 이름·기간 수정. 기간이 줄어 사라지는 Day의 블록은 삭제하지 않고 후보 블록으로 자동 이동. | 권장 |
| `GRP-04` | **프로젝트 삭제** | 멤버 누구나 요청 가능하나 확인 모달 필수. 완료된 프로젝트 삭제는 관리자만. | 권장 |
| `GRP-05` | **프로젝트 카드 진입 분기** | **카드 클릭**: 상태와 무관하게 **프로젝트 대시보드로 진입하며 편집이 가능하다**(완료 프로젝트도 동일 — RO-01). 완료 프로젝트는 진입 시 상단에 안내 배너 + 열람 모드 토글이 함께 표시된다. | 필수 |
| `GRP-06` | **멤버 목록 · 초대** | 멤버 리스트(프로필, 닉네임, 방장 뱃지, 접속 상태). 초대 코드 표시 + 복사 버튼. 관리자는 코드 재발급 가능(기존 코드 즉시 무효화). 코드 유효기간 7일. | 필수 |
| `GRP-07` | **멤버 방출** | 관리자만. 확인 모달 후 즉시 그룹 접근 차단. 방출된 멤버의 블록은 유지(작성자 표기 유지). 방출자는 동일 코드로 재입장 불가(코드 재발급 필요). | 권장 |
| `GRP-09` | **그룹 탈퇴 (자발적)** | 멤버 본인이 그룹에서 나가는 경로. 그룹 페이지 멤버 목록 하단 "그룹 나가기" + 확인 모달. 처리 규칙:<br>· 작성한 블록은 **그룹 자산으로 유지**(탈퇴 후 작성자는 "탈퇴한 멤버"로 표시)<br>· 진행 중 프로젝트의 접속·편집 세션은 즉시 종료, 보이스 채널에서 강제 퇴장<br>· **방장이 탈퇴**하는 경우 가입일이 가장 오래된 멤버에게 관리자 권한 자동 위임(02장 참조). 위임 대상이 없는 마지막 1인의 탈퇴는 그룹 소프트 삭제로 처리하며, 모달에서 이 사실을 명확히 고지<br>· 탈퇴 후 재입장은 유효한 초대 코드로 가능(방출된 멤버와 달리 코드 재발급 불필요)<br>· 멤버 수 변동은 1인 예산 값에 즉시 반영(BGT-03) — 팀 총액 자체는 변하지 않는다 | 필수 |
| `GRP-10` | **여행 완료 처리 · 상태 전환** | 대시보드의 **"여행 완료"** 버튼(확인 모달, 멤버 누구나) → 프로젝트 상태 `DONE` 전환, `done_at` 기록. **완료는 되돌릴 수 있고, 완료 후에도 편집이 가능하다.** 완료된 프로젝트의 대시보드에는 **"다시 계획으로"** 버튼이 표시되어 언제든 `PLANNING`으로 되돌릴 수 있다(멤버 누구나, 횟수·기한 제한 없음). 완료 버튼은 열람 모드에서는 숨겨진다(RO-02). | 필수 |

## 07. D. 프로젝트 대시보드 `DASH`

서비스의 핵심 화면. **3단 레이아웃** — 좌측 Day 탭 컬럼 / 중앙 보드(체인 + 후보 블록) / 우측 위젯(예산·지도·장소 검색). 접속 중인 멤버는 상단 바 아바타로 표시한다(PRS-01). 챗봇은 우하단 플로팅 버튼, 보이스는 하단 중앙 고정 바. 편집 모드의 체인 영역은 자체 스크롤 컨테이너(최대 높이 제한)로 동작해, Day의 블록이 많아져도 화면을 새로고침하거나 페이지 전체를 크게 스크롤하지 않고 하단의 후보 목록이 항상 함께 보인다. 모든 편집은 실시간으로 전 멤버에게 동기화된다(NFR-01).

### D-1. Day 탭 `DAY`

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `DAY-01` | **Day 탭 네비게이션** | 보드 **좌측에 세로로 고정된 책갈피 형태의 탭 컬럼**으로 DAY 1 ~ DAY n을 자동 생성해 나열한다(가로 스크롤 탭 바 아님). 각 탭에 해당 Day의 블록 개수 뱃지 표시, 탭 클릭 시 해당 일자의 체인만 표시(활성 탭은 진한 배경 + 액센트 컬러 테두리로 강조). 일자 헤더에 날짜·시작 시각·종료 예상 시각 표시. 탭 컬럼은 보드 스크롤과 무관하게 상단에 sticky로 고정된다. 최대 14일(NFR-04) 기준으로 검증하며, 그 이상은 탭 컬럼 자체가 세로 스크롤된다. 열람 모드에서는 숨겨지고 전체 Day가 스크롤 한 화면에 나열된다(RO-02). | 필수 |
| `DAY-02` | **탭 드롭으로 일자 이동** | 블록(체인·후보·챗봇 카드)을 Day 탭 위에 드롭하면 그 일자의 체인 끝에 삽입되고 화면이 해당 Day로 전환. 드래그 오버 시 탭에 금색 하이라이트. | 필수 |
| `DAY-03` | **Day 시작 시각** | Day별 시작 시각 설정(기본 09:00). BLK-08 시간 재계산의 기준값. | 권장 |

### D-2. 블록 `BLK`

## 08. E. 열람 모드 `RO`

보드를 읽기 전용으로 보는 **보기 옵션**이다. 완료된 프로젝트를 "계획했던 블록을 다시 본다"는 목적으로 훑을 때, 또는 편집 중 실수로 블록을 건드리고 싶지 않을 때 사용한다.

> **전제 — 완료는 잠금이 아니다.** 프로젝트 상태(`PLANNING` ↔ `DONE`)는 표시용 값일 뿐이며, **완료 후에도 모든 편집이 가능하다**(GRP-10). 여행 중 바뀐 일정을 사후에 기록하거나, 실수로 누른 완료를 되돌리거나, 빠뜨린 세부 내용을 나중에 채워 넣는 일은 모두 정상 시나리오다. 열람 모드는 사용자가 **직접 켜고 끄는 토글**이며, 프로젝트 상태와 무관하게 시스템이 강제로 적용하지 않는다.

| ID | 기능 | 상세 사양 | 우선순위 |
|---|---|---|---|
| `RO-01` | **열람 모드 토글** | 대시보드 상단에 편집/열람 모드 토글을 상시 제공한다. 프로젝트 상태(계획 중/완료)와 무관하게 언제든 켜고 끌 수 있으며, **켜짐 상태는 본인 화면에만 적용된다**(클라이언트 로컬 설정 — 다른 멤버의 편집을 막지 않는다. 서버 전송·DB 저장 없음). 프로젝트 상태에 따른 기본값 차등(예: 완료 시 자동 켜짐)은 두지 않는다 — 진입 시 항상 마지막으로 선택한 모드를 유지한다. | 필수 |
| `RO-02` | **읽기 전용 표시 범위 — 전체 Day 스크롤 열람으로 전환** | 열람 모드는 같은 화면을 잠그기만 하는 것이 아니라, **Day 탭으로 하루씩 넘겨보던 편집 화면을 전체 여행 일정을 위에서 아래로 훑어보는 화면으로 바꾼다**. 켜지는 동안 본인 화면에서:<br>· **Day 탭 컬럼, 우측 위젯(예산·지도·장소 검색), 후보 목록**을 모두 숨기고 1단 레이아웃으로 전환한다. 보드 영역 하나에 Day 1부터 마지막 Day까지 구간별 제목과 함께 순서대로 모두 표시되며, Day를 눌러 전환하는 대신 스크롤로 전체를 훑어본다. 일정이 없는 Day는 "일정 없음"으로 표시<br>· 드래그(블록·후보·챗봇 카드·Day 탭 드롭, 소요 시간 리사이즈 핸들 포함) 비활성, 상태 전환 버튼·챗봇 FAB·블록 추가 버튼 숨김<br>· 보이스 참여, 타 멤버 접속·커서 확인은 상단 바·보드 위에 그대로 유지되어 계속 가능<br>**타 멤버가 편집한 내용은 열람 모드에서도 실시간으로 반영된다**(NFR-01 — 읽기 전용은 입력만 막을 뿐 동기화를 끊지 않는다). | 필수 |
| `RO-03` | **블록 상세 열람** | 열람 모드에서 블록 클릭 시 상세 모달이 열리되 입력 필드 비활성, 저장 버튼 숨김. 시간·예산·세부 내용을 열람만 한다. 모달 하단에 "편집하려면 열람 모드를 꺼주세요" 안내 + 원클릭 해제 버튼 제공. | 필수 |

> **서버 정책** — 프로젝트 상태에 따른 쓰기 op 거부는 두지 않는다. 완료 프로젝트에도 일반 프로젝트와 동일한 권한 규칙(그룹 멤버십 검증)만 적용된다(NFR-05).

## 09. 비기능 요구사항 `NFR`

| ID | 항목 | 사양 |
|---|---|---|
| `NFR-01` | **실시간 동기화** | WebSocket + STOMP. 프로젝트 단위 토픽 `/topic/project/{id}`. 모든 변경은 서버 검증 → DB 반영 → 순서 번호(seq)를 붙인 op로 브로드캐스트(서버 권위 모델). 클라이언트는 낙관적 UI 적용 후 서버 op로 확정/롤백. 재연결 시 마지막 수신 seq 이후 op 재전송 또는 스냅샷 재로딩. |
| `NFR-02` | **동시성 — 필드/순서** | **블록 필드: 필드 단위 LWW(Last-Write-Wins)**.<br>· op는 **변경된 필드만** 담아 전송한다(`{block_id, field, value, client_ts}`). 서버는 `UPDATE block SET <field>=?, <field>_updated_at=? WHERE id=? AND <field>_updated_at < ?` 형태로 **해당 필드만** 갱신하고, 더 오래된 op는 조용히 무시한다<br>· 서로 다른 필드에 대한 동시 편집은 **구조적으로 충돌하지 않는다**(예산과 소요 시간은 독립). 같은 필드 동시 편집만 나중 값이 이기며, 진 쪽에는 서버 op로 최신값이 밀려와 화면이 정정된다<br>· 시각 기준은 **서버 수신 시각**을 사용한다(클라이언트 시계 신뢰 금지). 필드별 갱신 시각의 스키마 형태는 OI-04<br>· **긴 텍스트 필드는 예외** — NFR-03 참조<br>**블록 순서**: fractional indexing 문자열 키 — 이동 시 1행만 갱신, 동시 삽입도 충돌 없음. Day 간 이동은 `day_no` + `order_key` 동시 갱신 1건. |
| `NFR-03` | **동시성 — 긴 텍스트 필드** | 세부 내용(최대 500자)은 LWW를 그대로 적용하면 **입력 중이던 문장 전체가 통째로 날아가는** 유일한 필드다. 정책 후보는 아래 두 가지이며 **구현 담당자 간 합의로 결정한다(OI-04)**:<br>· **(a) 텍스트 필드 한정 편집 락** — Redis `SET NX`, TTL 30초 + 10초 하트비트. 락 보유자만 저장 가능, 타 멤버는 해당 **텍스트 영역만** 읽기 전용(블록의 다른 필드는 자유롭게 편집 가능). 구현 단순, 동시 작성 불가<br>· **(b) 필드 단위 LWW + 덮어쓰기 경고** — 저장 시점에 서버 값이 내가 연 시점보다 새로우면 저장을 보류하고 diff 안내("○○님이 먼저 수정했어요 — 덮어쓰기 / 내 변경 취소"). 락 없음, 구현 중간, 동시 작성 시 한쪽 손실<br>권고: v1은 (a). 텍스트 필드는 편집 빈도가 낮아 락 대기의 체감 비용이 작고, 락 범위가 블록이 아닌 필드로 좁으므로 협업을 막지 않는다.<br>**1회성 작업**(챗봇 초기 생성 등)은 위 논의와 무관하게 Redis 분산 락으로 중복 실행 방지. |
| `NFR-04` | **성능 목표** | op 브로드캐스트 왕복 < 300ms(동일 리전), 대시보드 최초 로딩 < 2s, 프로젝트당 블록 최대 200개·Day 최대 14일, 동시 접속 그룹당 10명 기준 무리 없는 동작. |
| `NFR-05` | **보안** | 모든 API JWT 인증. 그룹 리소스 접근 시 멤버십 검증(서버). **프로젝트 상태(`DONE`)에 따른 쓰기 op 거부는 두지 않는다** — 완료는 표시용 상태 값이며 편집 권한은 상태와 무관하게 그룹 멤버십으로만 판정한다(RO-01). 초대 코드는 추측 불가 랜덤 8자(혼동되는 `I·O·0·1` 제외) + 7일 만료 + 재발급 시 무효화. WebSocket 연결 시에도 토큰 검증. |
| `NFR-06` | **인프라** | Spring Boot + MySQL(RDS) + Redis, EC2 + Docker. 단일 서버 시작 — scale-out 시 STOMP 브로커 릴레이 또는 Redis Pub/Sub으로 서버 간 op 중계 전환. |
| `NFR-07` | **반응형** | 데스크톱 우선. 모바일(≥360px)에서 열람·간단 편집 가능해야 함(드래그는 터치 이벤트 지원 라이브러리 사용). 챗봇 패널·보이스 바는 모바일에서 전체 폭 하단 시트로 전환. |

> 1. **ODsay API 신청 승인 여부**를 개발 착수 전에 확인할 것. 버스·지하철 길찾기는 **필수** 기능이므로 API 가용 여부가 일정에 직접 영향을 준다. 미승인·지연 시 직선거리 추정 + 수동 입력만으로 기능이 성립하도록 설계되어 있으나(BLK-04), **어느 단계로 갈지는 개발 초기에 확정**해야 UI(추정치 뱃지 노출 여부)가 정해진다. 택시는 API 연동 없이 거리 기반 산식으로만 동작하므로 이 리스크에서 자유롭다.
> 2. **TAGO API 신청·쿼터**를 확인할 것. KTX 시간표 후보 계산의 유일한 데이터원이다.
> 3. **카카오 로컬 API 무료 쿼터**(일 100,000건) 확인. MAP-02 검색 디바운스 + BOT-02 후보 생성이 주 소비처.
> 4. **좌표→주소 변환(coord2address)** 은 MAP-04의 핀 직접 지정에서 쓰이는 엔드포인트이므로 쿼터 산정에 포함할 것.

## 11. 데이터 모델 개요

```
member (id, provider, provider_id, nickname, profile_img, created_at)
group_ (id, name, invite_code, invite_expires_at, owner_id, deleted_at)
group_member (group_id, member_id, role[ADMIN|MEMBER], joined_at)
project (id, group_id, name, start_date, end_date,
         destination(GRP-02·nullable), main_transport(GRP-02·nullable),
         keywords(챗봇 입력 후 저장·nullable),
         budget_headcount(정산 기준 인원·GRP-02 입력값이 초기값, 이후 직접 재지정 가능),
         budget_target(희망 총 예산·BGT-02·nullable=미설정),
         status[PLANNING|DONE], done_at(되돌리면 null), created_at)
block (id, project_id, day_no(null=후보), order_key(fractional), category, sub_category,
       name, address, duration_min, is_instant(단일 시각 블록 여부 ─ BLK-01),
       budget(해당 블록의 팀 전체 금액 ─ BLK-01·BGT-01), detail,
       lat, lng, place_id,               ─ 장소성 블록은 lat/lng NOT NULL (MAP-04)
       transport_meta(JSON: 수단/열차유형/출발도착 시각·지점 등),
       source[KAKAO|MANUAL|BOT], author_id, last_edited_by(PRS-04),
       field_updated_at(JSON: 필드별 서버 수신 시각 ─ LWW 판정용, NFR-02),
       deleted_at)
activity_log (id, project_id, member_id, op_type, payload, seq, created_at)
```

**설계 원칙**
- `status`는 **양방향 전환**된다(`PLANNING` ↔ `DONE`). 완료를 편집 잠금 조건으로 사용하지 않는다(GRP-10)
- `place_id`에 **UNIQUE 제약을 두지 않는다** — 동일 장소 중복 등록 허용(MAP-03). 장소 식별·재조회용 참조 값으로만 사용
- 블록 단위 `version` 컬럼을 두지 않는다 — 동시성은 `field_updated_at` 기반 필드별 LWW로 처리(NFR-02). 컬럼 분리(`budget_updated_at`, `detail_updated_at` …) vs JSON 단일 컬럼은 **OI-04**에서 결정
- presence(접속·커서)와 텍스트 편집 락은 DB에 저장하지 않고 Redis/메모리에서만 관리한다
- 블록 시작 시각·Day 종료 예상 시각은 파생 계산값이므로 저장하지 않는다(BLK-08)
- `block.budget`은 항상 **팀 전체 금액**이다. 1인 금액은 `budget_headcount`로 나눈 파생값이므로 별도 컬럼으로 저장하지 않는다(BGT-01·BGT-03)

## 12. 오픈 이슈 (팀 결정 필요)

| ID | 이슈 | 선택지 / 권고 |
|---|---|---|
| `OI-01` | 여행 완료 트리거 — 버튼 수동 vs 종료일 자동 | 수동 버튼 + 종료일 다음날 리마인드 푸시(하이브리드) 권고. 완료가 되돌릴 수 있는 상태 전환이 되면서(GRP-10) 오조작 리스크가 사라졌으므로, **완료 권한은 멤버 전원 허용**을 권고한다. 남은 결정은 자동 전환 도입 여부. |
| `OI-02` | 보이스 mesh 인원 한계(6인) 초과 시 | 6인은 프로토콜 제약이 아닌 mesh의 대역폭·CPU 부담에서 온 v1 정책값(VOC-01 근거 참조). v1은 6인 제한 + "인원이 가득 찼어요" 안내. 그룹 정원 10명 전원이 동시 통화를 요구하는 사례가 확인되면 SFU(LiveKit·mediasoup 등) 도입 검토 — 미디어 서버 비용·운영 부담이 발생하므로 수요 확인 후 결정. |
| `OI-03` | 개인화 추천 데이터원 — 챗봇 개인화를 무엇으로 할지 | 후보: (a) 프로젝트 키워드 이력 (b) 블록 채택/제외 행동 로그. 권고: v1은 (a)로 시작 — 추가 입력 없이 확보되는 데이터. |
| `OI-04` | **긴 텍스트 필드(세부 내용) 동시 편집 정책** — **동시성 구현 담당자 회의로 결정** | 숫자·단일 선택 필드는 필드별 LWW로 확정되어 논의가 끝났고(NFR-02), 남은 결정은 텍스트 필드 하나다. 후보: **(a)** 텍스트 필드 한정 편집 락(Redis SET NX, TTL 30초) / **(b)** LWW + 덮어쓰기 경고 diff. 권고: v1은 (a) — 구현이 단순하고 락 범위가 필드로 좁아 협업을 막지 않는다. 함께 정할 것: ① `field_updated_at`을 컬럼 분리 vs JSON 단일 컬럼으로 둘지 ② 락 대기 중인 사용자에게 보여줄 UI. **결정 기한: 동시성 모듈 착수 전.** |
| `OI-05` | 교통 블록이 없는 구간의 이동 시간 처리 강도 | BLK-08은 현재 "0으로 계산 + 1km 초과 시 힌트 표시"(자동 삽입 없음)로 정의. 대안: 좌표 직선거리 기반 이동 시간을 **암묵적으로 자동 가산**. 후자는 시간 정확도가 오르지만 사용자가 만들지 않은 시간이 일정표에 끼어들어 혼란 소지. 권고: v1은 현행 유지(명시적 블록만 시간을 차지). |
