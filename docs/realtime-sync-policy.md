## 겪은 버그

**재현**: A·B가 같은 블록을 동시에 잡고, A가 10시 위치에 놓고 B가 11시 위치에 놓는다.

- 증상 1 — 나중에 놓은 B의 화면만 A의 옛 위치(10시)에 갇힌다. 서버·A는 11시(정상).
- 증상 2 — 먼저 놓은 A가 B의 변경을 아예 못 받는 경우가 있다.

## 원인

**대원칙 위반**: 모든 클라이언트가 수렴하려면 *화면 = seq 순서로 op를 전부 적용한 결과*여야 한다. 두 지점에서 이 불변식이 깨졌다.

1. **자기 op 일괄 스킵 × 드래그 중 유예 큐** (증상 1)
   드래그 중 도착한 원격 op는 유예 큐에 쌓였다가 드롭 후 flush되는데, 이 flush(남의 **옛** op)가 방금 만든 내 낙관 반영을 덮는다. 그걸 서버 최종값으로 되돌려줄 내 op의 에코는 "자기 op = 이미 반영됨"이라는 가정으로 스킵돼 버려진다. 그 가정은 사이에 남의 op가 끼는 순간 무너진다.

2. **재연결 유실은 "다음 op"가 와야만 드러남** (증상 2)
   연결이 잠깐 끊긴 사이의 op는 이후 op가 도착해 seq 갭이 생겨야 감지된다. 상대의 드롭이 마지막 op면 그 "다음"이 영영 없어서 못 따라잡는다.

## 해결 3종

### ① 자기 op도 종류별로 에코 적용 (일괄 스킵 금지)

시퀀서는 커서 전진을 위해 자기 op까지 전부 넘기고(자기 op도 seq를 소비한다), 적용 여부는 op 종류별로 정한다:

| op | own 처리 | 이유 |
|---|---|---|
| `BLOCK_MOVED` | **적용(에코)** | 마지막 쓰기 승리형 — 남의 op에 덮인 자리를 자기 에코가 제 위치로 재확정 |
| `BLOCK_FIELD_UPDATED` | **적용(에코)** | 서버가 스테일 필드를 payload에서 빼고 보내므로, seq 순서 덮어쓰기 = 서버 최종값. 화면 y좌표가 startMins라 이게 빠지면 위치를 재확정해도 시각이 남의 값으로 남는다 |
| `BLOCK_CREATED` | 스킵 | 낙관 생성은 임시 id → POST 응답에서 서버 id로 교체되는데, 에코가 끼어들면 같은 블록이 두 벌 생긴다 |
| `BLOCK_DELETED` | 스킵 | 이미 로컬 제거됨 + 재적용하면 자기 삭제에 "다른 멤버가 삭제했어요" 토스트가 뜬다 |
| `TARGET_BUDGET_CHANGED` | 스킵 | 디바운스 저장 중이라 과거 값 에코가 최신 입력 표시와 싸운다 |
| `PROJECT_UPDATED` | 스킵 | 자기 변경으로 보드 전체를 재시드할 이유가 없다 |

부칙: own `BLOCK_MOVED`인데 로컬에 그 블록이 없으면(옮긴 직후 지운 경우) reload하지 않고 무시한다.

### ② 재연결마다 즉시 따라잡기 — **미구현**

설계: `useProjectOps`의 `onConnected`(최초 연결·모든 재연결)에서 시퀀서 `syncNow()` → `GET /ops?afterSeq={cursor}`로 유실분을 바로 메꾼다. 다음 op를 기다리지 않는다.

> **현재 코드에 없다.** `syncNow`는 `opSequencer.js`에 정의되고 export되어 있으나 **호출부가 없다**(`frontend/src` 전수 검색). `useProjectOps`의 `onConnect`는 재구독만 하고 시퀀서를 깨우지 않는다. 따라서 **증상 2가 그대로 남아 있다** — 상대의 마지막 조작이 끊긴 구간에 있으면 다음 op가 오기 전까지 보드가 발산한 상태로 유지된다.
>
> 필요한 작업: `useProjectOps`에 `onConnected` 콜백을 추가하고 `sequencerRef.current?.syncNow()`를 배선.

### ③ 영구 갭 폴백 — **미구현**

설계: 갭 재시도 6회(~3초)에도 진전이 없으면 스냅샷 reload로 수렴. seq만 소비되고 롤백된 트랜잭션처럼 절대 메워지지 않는 갭에서 무한 대기하지 않기 위함.

> **현재 코드에 없다.** `opSequencer.js`는 `retryDelayMs = 500` 간격으로 **상한 없이 재시도**하며, reload 폴백도 경고 로그도 없다. 그런 갭을 만나면 `GET /ops`를 초당 2회 무한 폴링하고, 갭 이후 op는 버퍼에만 쌓여 **실시간 반영이 완전히 멈춘다.**
>
> 이 상황은 이론적 가정이 아니다. 서버가 커밋 전에 seq를 채번하므로(`OpPublisher`) 롤백된 트랜잭션은 저널에 영구 갭을 남긴다.
>
> 필요한 작업: 재시도 상한 + `reload()` 폴백 + 경고 로그.

## 검증됨

①에 대해서만: 같은 블록 동시 드래그(양방향 순서 모두) → 양쪽 화면이 마지막 드롭으로 수렴. 단독 편집 회귀 없음(에코가 낙관 반영과 같은 값이라 시각 변화 없음).

②·③은 미구현이라 검증 대상이 아니다.

## "임시조치"인 이유 / 남은 것

op별 own 스위치는 새 op 타입이 생길 때마다 정책을 다시 정해야 하는 임기응변 성격이 있다. 장기 선택지:

- ~~이 정책 표를 dashboard-api.md(§X-Client-Id)에 계약으로 승격~~ → **반영 완료.** `dashboard-api.md`의 "자기 op 에코 정책" 절이 이 표를 계약으로 담고 있다. 명세가 권했던 "일괄 스킵"은 삭제됐다
- 또는 낙관 반영을 버리고 서버 에코만으로 그리는 재설계(입력 지연이 생기는 트레이드오프)

새 op 타입 추가 시 **"own일 때 재적용해도 무해한가?"** 를 반드시 판단하고 위 표에 추가할 것. `dashboard-api.md` 쪽 표도 함께 갱신할 것 — 두 문서가 어긋나면 계약이 무의미해진다.

**미구현 ②·③은 별도 작업으로 남아 있다.** 이 문서가 "해결됨"으로 기술해 두는 바람에 실제로는 방어가 없는데 있다고 오인될 소지가 있었다.
